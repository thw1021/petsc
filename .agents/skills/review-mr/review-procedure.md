### 3. Read and review the diff
- For an MR, check that `sha` in `mr-<MR_IID>-meta.json` matches `diff_refs.head_sha` before
  reviewing. If they differ, fetch the diff and metadata again together; if they still differ,
  stop and report the mismatch. Do not review or post using inconsistent revisions.
- Review the file named by `DIFF_FILE`.
- Report any file the diff shows as binary (`Binary files ... differ` or `GIT binary patch`) as not covered.
- Review through to line `LINES`, in parts if needed. Do **not** re-run the diff per file.
- Focus on:
  - Bugs and correctness issues
  - Performance implications
  - Code quality, style, and documentation: check against conventions in @doc/developers/style.md
  - Unchecked or swallowed error returns (e.g. calls missing `PetscCall()`)
- Never review `.out` file *contents*; do flag mismatches between a code change and its reference output (missing update, unjustified regeneration, orphan file).
- PETSc error model: treat `PetscCall()`, `PetscCheck()`, `SETERRQ` as terminal — don't report leaks/un-restored arrays on fatal paths. Do report bugs on non-error paths or before the error fires.
- Classify each finding: CRITICAL / HIGH / MEDIUM / Style / LOW.
- A clean diff producing few or no findings is a valid outcome.

For MR reviews, identify temporary CI-selection commits generated by
`lib/petsc/bin/maint/runjobs.py`. The script uses commit subjects beginning
`DRAFT: CI: Temporary commit, remove before merge!` and adds a generated-command header to
`.gitlab-ci.yml`. Inspect the MR's commit list and the relevant commit patches to establish which
changes came from these commits; do not rely on a mention of `runjobs` alone.

Do not report findings about these temporary changes or count them as LOW, and do not post
comments about them. State their presence and exclusion in the coverage summary, including each
commit's SHA and title. Continue reviewing independent changes, including genuine CI changes in
the same file and changes to `runjobs.py` itself. If attribution is unclear, report the affected
coverage limitation rather than silently excluding the entire file. Keep `DIFF_FILE`, the
reviewed head SHA, and posting anchors unchanged; the exclusion affects review scope only.

Severity weights for PETSc — every finding must carry the evidence its kind of claim requires:
- **CRITICAL / HIGH / MEDIUM** — behavioral claims: correctness, performance, real bugs. State the **trigger** (concrete input or event; an MPI rank/partition condition counts) and **impact** (concrete consequence: wrong result, crash, hang, leak; a slowdown must name the affected operation). Discard claims whose trigger violates documented use unless the change breaks a documented guarantee for that case. Classify a confirmed issue as LOW when its impact is only a clumsy-but-accurate message, a lost convenience, or one cheap rerun (a test or CI job, not a production solve).
- **Style** — at par with MEDIUM; a real review blocker. Two kinds:
  - Convention violation: name the broken rule — the AGENTS.md clause, `doc/developers/style.md` section, or linter check. No trigger/impact; do not invent one ("someone reads the code" carries no information). Discard unsupported convention claims.
  - Factually wrong user-facing text (docstring, error message, docs): quote the text and state what the code actually does. Never LOW; higher than Style if following the text causes damage.
- **LOW** — confirmed minor issues only. Count, do not list; list individual LOW items only if asked. Disproved or unverified candidates do not count as LOW.

A design alternative is not a finding.

Calibration:
- MEDIUM: `VecRestoreArray()` missing on an early-return path — trigger: the `n == 0` fast path; impact: vector left locked, next `VecGetArray()` errors.
- Style: braces around a single-statement `if` — rule: AGENTS.md anti-pattern "Braces on single-statement if/else".
- Style: error message says "matrix" where it means "vector" — untrue published text, never LOW.
- LOW: error message awkward but accurate.

### 4. Verify each finding before reporting
Treat every candidate finding, including LOW candidates, as tentative. Verify it against
`DIFF_FILE` and, when more context is needed, the source at `SRC_SHA` or `MR_HEAD_SHA`. This
includes relevant callees, macros, and declarations. Do not use working-tree source as evidence
unless it matches that revision and the relevant files have no uncommitted changes. When the
CodeGraph index describes a different checkout, use it to locate symbols and relationships,
then read the evidence from the reviewed revision.

If the exact revision is unavailable and the diff lacks enough context, do not report the
finding. Record the affected path and the missing context as a verification limitation in the
coverage summary. Discard disproved or unsubstantiated candidates; do not count them as LOW.
Confirm that each surviving finding is real and actionable, classify it using Section 3, and
ensure its proposed fix preserves documented use and is proportionate to the issue.

### 5. Compose report
- Follow the human-facing writing rules in `AGENTS.md`. Write clear English for a reviewer who
  has not read the conversation; connect the problem, evidence, and proposed fix in complete
  sentences. Check grammar and readability before producing the report.
- Per finding: severity, file:line, description, its required evidence (Section 3), suggested fix.
  List each occurrence in the reviewed diff with file:line; do not use a representative example or
  "and similar elsewhere". Order CRITICAL → HIGH → MEDIUM → Style.
- State the coverage: files and lines reviewed, any path Section 3 reported as not covered,
  temporary `runjobs.py` commits excluded under Section 3, and any verification limitation
  recorded in Section 4. Include these limitations even when there
  are no findings at or above Style. End with `(N LOW findings suppressed; ask to show them.)`
  when `N > 0`.
- The report contains the findings, the coverage, the LOW count, and what other sections explicitly say to state — nothing else: no praise, no MR summary, no design commentary. If there are no findings at or above Style, say exactly that.
- Communicate unrelated workflow improvement suggestions to the user separately from the review
  report, following `AGENTS.md`. Do not count them as findings or post them as MR comments.

### 6. Write the merge-request report
For `review-mr` and `review-mr-post`, write the titled report to `ai-review.html`. Add a footnote
with the agent, version, model, and effort level actually used for this review, the current date
and time, `MR_IID`, `CI_PIPELINE_ID`, and `CI_JOB_ID`. Use `$CLAUDE_EFFORT` only when the review
was performed by Claude. Omit unavailable values; do not infer the running agent or model from
installed executables or unrelated environment settings.
